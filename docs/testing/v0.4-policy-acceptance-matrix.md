# v0.4 Policy Runtime 验收测试矩阵

状态：Stage 1 测试契约，等待 WEB-36 ADR 定稿后由核心开发 Agent 复核语义。

本矩阵把 `docs/roadmap.md` 的 v0.4 scope 和 acceptance criteria 转换为可执行的自动化测试。Stage 2 实现必须保留这些测试 ID；若 ADR 调整 public API，只可更新调用形式和精确错误码，不得删除对应行为断言。

## 质量门禁

- P0：安全边界或兼容性红线。任何失败均为 release blocker。
- P1：已承诺的 policy/CLI 行为。Stage 4 前必须自动化并全绿。
- P2：补充覆盖。失败必须有独立 Issue、owner 和风险说明。
- 禁止 `skip`、`only`、flaky retry、弱化断言和 `passWithNoTests`。
- 测试只使用本地 mock/fixture；不得访问外网、读取真实 secret 或依赖 wall-clock 等待。
- 时间相关行为使用 fake timers；HTTP 使用注入的 mock `fetch`；Prisma 使用内存 mock client；tRPC 通过本地 caller 执行。

## Fixture 契约

共享 baseline fixture 已在 `packages/core/test/fixtures/policy-tools.ts` 实现；Stage 2 在同一文件补齐依赖最终 ADR 的 invalid/conflict fixture。adapter 集成测试继续复用各 package 现有 fixture。所有 `run`、`fetch`、audit sink 和 Prisma delegate 都必须是可检查调用次数及参数的 spy。

| Fixture ID | 形态 | 必要字段 | 用途 |
| --- | --- | --- | --- |
| `FX-READ-ZOD` | 手写只读 tool | `source.kind=zod`、`capability=read`、`rowLimit=25`、`outputLimit=4096` | allow、read-only、limit、result stringification |
| `FX-WRITE-OPENAPI` | OpenAPI `POST /things` | `capability=write`、`hasAudit=false`、`hasPreviewToken=false`、mock `fetch` | mutating reject、unsafe metadata、adapter 回归 |
| `FX-WRITE-PRISMA-SAFE` | Prisma `User.create` | `capability=write`、`hasAudit=true`、`hasPreviewToken=true`、mock delegate/audit | safety requirements、allowed commit |
| `FX-WRITE-TRPC` | allowlisted tRPC mutation | `capability=write`、`requiresAuthOrContext=true`、本地 caller | source/name rules、adapter 回归 |
| `FX-NO-METADATA` | 手写 tool | 不提供 `metadata` | configured policy fail-closed、无 policy 兼容 |
| `FX-INVALID-METADATA` | runtime-invalid tool | 通过 `unknown` 边界注入未知 `source.kind`、非布尔 safety 或非数值 limit | 防御式 fail-closed，不依赖 TypeScript 绕过运行时校验 |
| `FX-CONFLICT-METADATA` | 矛盾 metadata | `capability=write` 且 safety 组合不能满足已启用要求 | 冲突/部分满足规则仍拒绝 |
| `FX-NO-POLICY` | 现有 adapter 与 transport 输入 | 原始 `BridgentTool[]`，不调用 policy API | v0.3 行为 baseline |

| `POL-U-003` | read-only policy 调用 `FX-WRITE-OPENAPI` | 在 `run` 前拒绝；`run=0` | P0 |
| `POL-U-004` | read-only policy 调用 `FX-READ-ZOD` | 允许；`run=1`；结果不变 | P0 |
| `POL-U-005` | 要求 audit 时 mutating tool 缺 metadata/缺 `hasAudit` | fail closed；区分 missing 与 false；`run=0` | P0 |
| `POL-U-006` | 要求 preview token 时 `hasPreviewToken=false` | fail closed；指出必需字段；`run=0` | P0 |
| `POL-U-007` | 同时要求 audit + preview，fixture 只满足一项 | 不得部分放行；错误列出未满足项；`run=0` | P0 |
| `POL-U-008` | configured policy 遇到 `FX-NO-METADATA` | 无法求值即 fail closed；不得默认为 read；`run=0` | P0 |
| `POL-U-009` | configured policy 遇到 `FX-INVALID-METADATA` | 不抛出未处理异常；返回 policy error；`run=0` | P0 |
| `POL-U-010` | 同一 tool 同时命中 allow 与 deny | 按 ADR 的确定性优先级执行；不得依赖配置顺序；deny 场景 `run=0` | P0 |
| `POL-U-011` | source kind allow/deny 命中与未命中 | 对 `openapi`、`prisma`、`trpc` 分别断言；错误带 source kind | P1 |

| `POL-U-016` | 启用 limit rule 但对应 hint 缺失/非法 | 无法求值即 fail closed；`run=0` | P0 |
| `POL-U-017` | policy 未启用某项 limit rule | 缺失该 hint 不影响其他可求值规则 | P1 |
| `POL-U-018` | allowed call 返回 object/string | object/string 均保持现有 `registerTools` stringification 契约 | P0 |
| `POL-U-019` | policy reject handler 自身被重复调用 | 每次结果确定、无全局状态泄漏、原始 `run=0` | P1 |

## 2026-08-17 no-policy baseline

基线 commit：`2a416dbba1c9416f3069e20b8b396051179b0d0e`（`origin/main`）。

环境：Darwin 25.6.0 arm64、Node 25.2.1（满足 Node >=22.18）、pnpm 10.34.1、Turbo 2.9.16。

执行命令：

```bash
pnpm install --frozen-lockfile
pnpm turbo run build test typecheck lint
```

结果：30/30 Turbo tasks 成功，7 个 Vitest workspace、28 个 test files、132 个 tests 全绿；docs build、全部 typecheck/lint 通过。未访问外网测试端点，未使用真实凭证。安装阶段在首次 build 前出现 workspace CLI bin 尚未生成的 warning，随 build 生成 `packages/cli/dist/cli.mjs` 后 smoke test 正常通过，不构成 blocker。

基线审计发现 `packages/cli/package.json` 使用 `vitest run --passWithNoTests`。CLI 当时实际执行了 17 个 tests，但该 flag 会允许未来空测试假绿，因此 WEB-33 移除它，并要求最终 gate 在无此 flag 下复验。

WEB-33 修改后复验：同一全量命令 30/30 tasks 成功；core 新增 2 个 baseline tests 后，最终为 29 个 test files、134 个 tests 全绿。CLI 明确以 `vitest run` 执行并通过 17/17 tests；测试卫生扫描和 `git diff --check` 均无命中/错误。

## WEB-36 ADR 合并检查表

WEB-36 定稿后，核心开发 Agent 复核本矩阵时必须逐项确认：

- public API 名称与 policy 注入边界；
- allow/deny 以及 tool/source 组合规则的固定优先级；
- 初始化期与调用期分别负责哪些校验；
- metadata 缺失、非法、矛盾及未知 future field 的 fail-closed 语义；
- MCP error 的稳定 code、结构和 remediation 文案；
- max tool count 与 row/output hint 的边界值语义；
- inspect summary 中 policy enabled/disabled/enforced 的序列化结构。

复核只更新表格中的 API/错误细节和 ADR 引用。任何删除 P0 行为覆盖的变更，都必须同步更新 roadmap acceptance criterion 或建立明确的 scope-change Issue。
